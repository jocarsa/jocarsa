## Cómo intento escribir software

Intento mantener algunas ideas constantes independientemente del lenguaje o del proyecto.

**Código comprensible antes que código sofisticado.**

Si puedo resolver correctamente un problema con una solución sencilla, normalmente prefiero esa solución.

**Pocas dependencias.**

Una dependencia tiene sentido cuando aporta algo importante. No simplemente porque exista.

**Datos bajo control.**

Siempre que sea razonable prefiero formatos, bases de datos e infraestructura que pueda administrar directamente.

**Automatizar lo repetitivo.**

Si una operación tiene que realizarse muchas veces, probablemente debería convertirse en código.

**Entender todas las capas.**

Frontend, backend, base de datos, red, servidor y sistema operativo forman parte de la misma aplicación.

**Documentar.**

El código explica cómo funciona algo. La documentación debería explicar además por qué funciona así.

**Construir para aprender.**

Una de las mejores formas que conozco de entender una tecnología es intentar construir algo con ella.

## Filosofía de trabajo

No busco utilizar una tecnología porque esté de moda.

Intento entender primero el problema.

Después intento reducirlo a sus elementos esenciales.

Y finalmente construyo una solución que pueda comprender, mantener y modificar.

En muchos casos eso significa desarrollar mi propio software.

En otros significa integrar herramientas existentes.

Y en otros simplemente escribir cincuenta líneas de Python que eliminan varias horas de trabajo manual.

Para mí, una buena solución tecnológica no es necesariamente la que utiliza más tecnología.

Es la que resuelve correctamente el problema con la menor complejidad razonable.
